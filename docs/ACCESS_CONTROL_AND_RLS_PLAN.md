## 1. Architecture Verification (Google OAuth + HMAC + Supabase Auth + Realtime)

Before tightening any PostgreSQL role privilege or RLS policy, we verified every client-side and server-side database call site across `src/`:

1. **Zero Direct Client Table Reads/Writes**: Scanning `src/` outside `src/server/` confirmed there are **zero** browser `supabase.from(...)`, `supabase.rpc(...)`, or `supabase.storage` calls.
   - Customer checkout, cart sync, wishlist, addresses, profile, welcome gate, product reviews, contact messages, newsletter subscription, and order tracking execute exclusively inside TanStack Start server functions (`src/server/*.ts`), which connect via `supabaseAdmin` (`SUPABASE_SERVICE_ROLE_KEY`, bypassing RLS) or `getDb()` (`postgres`, direct connection) after verifying server-side session tokens (`getAuthenticatedCustomerId`, `checkGoogleSessionServerFn`).
   - Admin mutations and data fetches execute exclusively inside `src/server/admin.ts` using `resolveAuthorizedAdmin`, checking live `admin_users.is_active`, `user_roles`, and `admin_whitelist`.
2. **Google Direct Auth (HMAC JWT) Compatibility**:
   - Users logging in via Google OAuth hold server-signed HS256 JWTs (`SESSION_SECRET`). Those requests verify cryptographically on the server and operate through `service_role` / `postgres`. Tightening PostgREST `anon`/`authenticated` RLS causes **zero breakage** for Google-authenticated customers or admins.
3. **Supabase Realtime Compatibility (`account.tsx` & `admin.tsx`)**:
   - The **only** direct client Supabase usage is `supabase.channel(...).on("postgres_changes", ...)` in [account.tsx](file:///c:/Users/akhil/Downloads/cavenhurst-heritage-market/src/routes/account.tsx) and [admin.tsx](file:///c:/Users/akhil/Downloads/cavenhurst-heritage-market/src/routes/admin.tsx) when an authenticated Supabase GoTrue JWT session is active.
   - To preserve browser Realtime seamlessly:
     - **Customer Realtime** retains strict `SELECT` RLS `TO authenticated` matching `((SELECT auth.uid())::text)` / `(SELECT auth.uid())` on `orders`, `payments`, `payment_refunds`, `shipments`, `shipment_tracking_events`, `returns`, `customer_profiles`, `customer_addresses`, `customer_welcome`, `notifications`, and `support_tickets`.
     - **Admin Realtime** retains `SELECT` RLS `TO authenticated` matching `(SELECT public.is_admin())` across administrative operational tables (`orders`, `payments`, `shipments`, `product_reviews`, `contact_messages`, `admin_audit_logs`, etc.). Admins signed in via Google HMAC fall back cleanly to the 30-second server-function polling already implemented in `admin.tsx`.
4. **Performance & Multi-Permissive Design**:
   - All policies wrap `auth.uid()`, `auth.jwt()`, `public.is_admin()`, and `public.requesting_user_id()` inside scalar subqueries (`(SELECT ...)`) to satisfy PostgreSQL `initPlan` evaluation caching (`1` evaluation per statement instead of per row). Deprecated `auth.role()` is avoided in favor of explicit role targets (`TO anon` / `TO authenticated`) and JWT role claim checks (`request.jwt.claim.role` / `request.jwt.claims`).
   - Group A tables whose policies reference `public.is_admin()` (`products`, `product_images`, `product_variants`) split `SELECT` into `*_anon_select` (`TO anon`, without calling `is_admin()`) and `*_select_policy` (`TO authenticated`, with `OR (SELECT public.is_admin())`) so `anon` has zero indirect execution path to `is_admin()`.
   - Every `(table, role, action)` tuple has **at most ONE permissive policy** (combining `owner OR is_admin()` or `public_condition OR is_admin()` in a single rule, and splitting admin `INSERT`/`UPDATE`/`DELETE` policies out of `FOR ALL`), eliminating all `61` overlapping permissive policy advisor warnings at the same time.
